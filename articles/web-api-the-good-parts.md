## はじめに
直近の業務で、社内システム間を連携するためのREST APIを新たに設計する機会がありました。

これまでも既存のAPIを利用した開発や改修に携わることはありましたが、APIの設計方針そのものを考える機会はそれほど多くありませんでした。
そのため、「どのようなURL設計が分かりやすいのか」「レスポンス形式はどうあるべきか」「将来的な変更を見据えてどのような設計をすべきか」といった点を体系的に学びたいと考えるようになりました。

また、近年はAIの支援によって実装そのもののハードルは下がりつつあります。
一方で、APIの責務やリソース設計といった設計判断は依然として人間が担う領域です。
そのため、この機会にAPI設計の基本を改めて学びたいと思い、[Web API: The Good Parts](https://www.oreilly.co.jp/books/9784873116860/)を手に取りました。

本記事では、本書を読みながら特に印象に残った内容や、実務で活かせそうだと感じたポイントをまとめていきます。

## 対象読者
- REST APIをこれから設計する人
- APIは普段使うが、設計を体系的に学んだことがない人
- PMやテックリードとしてAPI設計の基本を押さえたい人


### APIエンドポイント設計で意識したいこと

APIのエンドポイントは、利用者が最初に目にするインターフェースです。そのため、実装都合ではなく「利用する開発者が理解しやすいか」という観点で設計することが重要だと感じました。

### URIを見ただけで役割が分かるようにする

エンドポイントは、そのURIを見ただけで何を扱うAPIなのか想像できる状態が理想です。

例えば `/products/12345` であれば「商品ID 12345の商品情報を扱う」と推測できます。
一方で、`/getdata?id=12345` のようなURIでは、何のデータを取得するAPIなのか判断できません。

APIを利用する開発者は仕様書だけでなくURIそのものも参考にするため、リソース名を明確に表現することが大切です。

### シンプルなURIを心がける

URIには必要以上の情報を含めない方が分かりやすくなります。

例えば、

* `/products/12345`
* `/users/100`

のような形式であれば、どのリソースを扱うAPIなのか一目で分かります。

一方で、

* `/service/api/getProductInformation/product/12345`

のように実装上の都合や冗長な表現が含まれると、可読性が低下してしまいます。

### 略語よりも分かりやすさを優先する

URIは開発者同士の共通言語でもあります。

そのため、文字数を減らすことよりも、誰が見ても意味を理解できることを優先した方がよいとされています。

例えば `products` を `prod` にしたり、`users` を `usr` にしたりすると、プロジェクト参加者によって解釈が分かれる可能性があります。

### 命名ルールを統一する

エンドポイントごとに命名規則が異なると、利用者は毎回ルールを覚え直さなければなりません。

例えばREST APIでは、

* 作成: `POST /products`
* 取得: `GET /products/{id}`
* 更新: `PUT /products/{id}`
* 削除: `DELETE /products/{id}`

のように、HTTPメソッドで操作を表現する設計が一般的です。

リソース名とHTTPメソッドの役割を統一することで、API全体の学習コストを下げられます。

### 将来の拡張を考慮した構造にする

APIは一度作って終わりではなく、後から機能追加されることがほとんどです。

そのため、新しい関連リソースを自然に追加できる構造にしておくと運用しやすくなります。

例えば商品レビュー機能を追加する場合、

`/products/{id}/reviews`

のような形で関連性を表現できれば、利用者も迷いにくくなります。

### 実装の都合をURIに持ち込まない

興味深かったのは、「URIにサーバ側の事情を反映させない」という考え方です。

利用者が知りたいのは「どのリソースにアクセスできるか」であり、そのデータがデータベースに保存されているのか、別サービスから取得されているのかは本来関係ありません。

そのため、

`/database/products/12345`

のような実装依存のURIではなく、

`/products/12345`

のようにリソースを中心に表現する方が変更にも強い設計になります。

## HTTPメソッドとエンドポイントの役割分担

REST APIでは、URIとHTTPメソッドを組み合わせてリソースを操作します。

ここで重要なのは、「何を操作するのか」はURIで表現し、「どのような操作をするのか」はHTTPメソッドで表現するという考え方です。

例えば、ユーザー情報を扱うAPIであれば、`/users/123` というURIが対象リソースを表し、取得・更新・削除といった操作はHTTPメソッドによって区別します。

| 操作 | HTTPメソッド    | 例                 |
| -- | ----------- | ----------------- |
| 取得 | GET         | GET /users/123    |
| 作成 | POST        | POST /users       |
| 更新 | PUT / PATCH | PUT /users/123    |
| 削除 | DELETE      | DELETE /users/123 |

このように役割を分離することで、URIの設計がシンプルになり、API全体の一貫性も保ちやすくなります。

### GETはデータ取得のために利用する

GETはリソースを取得するためのメソッドです。

例えばユーザー情報の取得であれば、以下のような形になります。

```text
GET /users/123
```

GETは原則としてサーバー上の状態を変更しない操作に利用します。そのため、GETリクエストを実行しただけでデータが更新されたり削除されたりする設計は避けるべきとされています。

### POSTは新しいリソースの作成に利用する

POSTは新しいリソースを登録する際に使用します。

```text
POST /users
```

REST APIでは、作成処理を表現するために `/createUser` のようなURIを作るのではなく、HTTPメソッド側で「作成」という意味を表現します。

### PUTとPATCHは更新処理で使い分ける

更新系の処理ではPUTとPATCHが利用されます。

PUTはリソース全体を更新するケースで利用されます。

```text
PUT /users/123
```

一方でPATCHは、一部の項目だけを変更したい場合に利用します。

```text
PATCH /users/123
```

実際の業務でもプロフィールの一部だけを更新するケースは多いため、PATCHが採用される場面は少なくありません。

### DELETEはリソース削除を表現する

リソースの削除にはDELETEを利用します。

```text
DELETE /users/123
```

削除処理であっても `/deleteUser` のようなURIを作る必要はなく、HTTPメソッドが削除という意味を表現します。

## SNSを例に考えるエンドポイント設計

本書ではSNSを例にエンドポイント設計が説明されていました。

### リソース名は複数形で表現する

リソースの集合を表す場合は複数形を利用します。

```text
/users
/posts
/friends
```

複数形に統一することで、API全体の命名ルールが分かりやすくなります。

### リソースIDで個別データを表現する

特定のユーザーを表す場合はIDをパスに含めます。

```text
/users/123
```

これにより、「ユーザー一覧」と「特定ユーザー」を自然に区別できます。

### 関係性はURIの階層で表現する

SNSではユーザーと友達のように関連するデータが存在します。

例えば、特定ユーザーの友達一覧を取得する場合は以下のようなURIが考えられます。

```text
/users/123/friends
```

この形式であれば、どのリソースに紐づくデータなのかが直感的に理解できます。

### 検索や絞り込みにはクエリパラメータを利用する

一覧取得時の検索条件はクエリパラメータで表現します。

```text
GET /users?name=john
GET /users?age=30
```

URIの構造を増やさずに検索条件を追加できるため、柔軟なAPI設計が可能になります。

### 設計時は認可も合わせて考える

エンドポイントを設計する際は、URIやHTTPメソッドだけでなく「誰が実行できるのか」も重要です。

例えば、

* 自分のプロフィールは更新できる
* 他人のプロフィールは更新できない

といった認可ルールを考慮しながら設計する必要があります。

API設計ではエンドポイントそのものに目が向きがちですが、実際の運用を考えると認可設計も同じくらい重要だと感じました。

## 検索機能とクエリパラメータ設計

一覧APIを設計する際には、「どのようにデータを検索するか」「大量のデータをどのように分割して取得するか」を考える必要があります。

特に利用者数やデータ量が増えるサービスでは、検索条件やページネーションの設計がAPIの使いやすさやパフォーマンスに大きく影響します。

### 一覧取得ではページネーションが重要

例えばユーザー一覧や投稿一覧を取得するAPIで、全件を一度に返してしまうとレスポンスサイズが大きくなり、通信量や処理時間が増加します。

そのため、多くのAPIではページネーションを利用して取得件数を制御します。

### 相対位置を利用したページネーション

比較的よく見かけるのが、件数やページ番号を指定する方法です。

```text id="egw7m1"
GET /users?limit=50&offset=100
```

この例では100件目から50件取得します。

または、

```text id="h1h5h7"
GET /users?per_page=50&page=3
```

のようにページ番号で指定する方法もあります。

実装しやすく利用者にも分かりやすい反面、データ量が増えると検索コストが高くなったり、取得中にデータが追加・削除された場合に結果がずれる可能性があります。

### 絶対位置を利用したページネーション

もう一つの方法として、IDや日時を基準に取得位置を指定する方法があります。

例えば、

```text id="zj8c2m"
GET /posts?max_id=1000
```

や

```text id="zv2u3p"
GET /posts?published_before=2026-07-20T00:00:00Z
```

のような形式です。

この方式は、特定の位置を基準にデータを取得するため、大量データでも効率的に検索しやすく、データ追加が頻繁に発生するサービスでも結果のずれが起きにくいという特徴があります。

SNSのタイムラインのような機能では、こちらの方式が採用されるケースも少なくありません。

### 検索条件はクエリパラメータで表現する

検索や絞り込みを行う場合は、クエリパラメータを利用します。

例えば特定の名前で検索する場合は次のようになります。

```text id="8o5h5v"
GET /users?first_name=ken
```

複数条件を組み合わせることもできます。

```text id="l5p0v3"
GET /users?first_name=ken&last_name=suzuki
```

### フリーワード検索という考え方

検索対象の項目を利用者に意識させたくない場合は、単一の検索パラメータを用意する方法もあります。

```text id="qb8n3a"
GET /users?q=ken
```

この場合、名前やメールアドレスなど複数の項目を横断して検索できるため、利用者にとって分かりやすいAPIになります。

### 実務で意識したいこと

本書を読んで印象的だったのは、「ページネーションは単なる画面表示の都合ではなく、API設計そのものに関わる重要な要素」という点です。

データ量が少ないうちはどの方式でも問題になりませんが、利用者数やデータ件数が増えるとパフォーマンスやデータ整合性に影響が出てきます。そのため、APIを設計する際は現在の要件だけでなく、将来的なデータ量も考慮してページネーション方式を選択することが重要だと感じました。

## Bearer Tokenを利用した認証

APIでは、利用者が誰であるかを識別し、アクセス権限を制御する仕組みが必要になります。

本書ではOAuth 2.0についても説明されていますが、ここでは実際のAPI利用時によく目にするBearer Tokenを中心に整理します。

### Bearer Tokenとは

Bearer Tokenは、APIへアクセスするための認証情報です。

ログインや認証処理を行った後に発行され、クライアントは以降のAPIリクエストでこのトークンを送信します。

サーバーは受け取ったトークンを検証し、リクエスト元のユーザーや権限を判断します。

### Authorizationヘッダーで送信する

Bearer TokenはHTTPヘッダーの`Authorization`に設定するのが一般的です。

```http
GET /users/me HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...
```

サーバー側はトークンを検証し、認証済みユーザーとしてリクエストを処理します。

### URLやリクエストボディでの送信は避ける

トークンはクエリパラメータやリクエストボディで送信することも技術的には可能ですが、一般的には推奨されていません。

例えば以下のような形式です。

```text
GET /users?access_token=xxxxx
```

URLはログやアクセス解析ツールに記録される可能性があるため、認証情報の漏洩リスクがあります。

そのため、多くのAPIではAuthorizationヘッダーを利用する方式が採用されています。

### 有効期限を設ける

アクセストークンには有効期限を設定することが一般的です。

もしトークンが漏洩した場合でも、有効期限が短ければ被害を限定できます。

また、有効期限切れ後は再認証やトークン更新処理を行うことで、セキュリティと利便性のバランスを取ることができます。

### スコープによる権限制御

Bearer Tokenには、どの機能にアクセスできるかという権限情報を持たせることがあります。

例えば、

* ユーザー情報の参照
* ユーザー情報の更新
* 管理者向け機能へのアクセス

といった権限を区別することで、必要最小限のアクセスのみを許可できます。
