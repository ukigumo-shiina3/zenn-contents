## はじめに
直近の業務で、社内システム間を連携するためのREST APIを新たに設計する機会がありました。

これまでも既存のAPIを利用した開発や改修に携わることはありましたが、APIの設計方針そのものを考える機会はそれほど多くありませんでした。
そのため、「どのようなURL設計が分かりやすいのか」、「レスポンス形式はどうあるべきか」、「将来的な変更を見据えてどのような設計をすべきか」といった点を体系的に学びたいと考えるようになりました。

また、近年はAIの支援によって実装そのもののハードルは下がりつつあります。
一方で、APIの責務やリソース設計といった設計判断は依然として人間が担う領域です。
そのため、この機会にAPI設計の基本を改めて学びたいと思い、[Web API: The Good Parts](https://www.oreilly.co.jp/books/9784873116860/)を手に取りました。

本記事では、本書を読みながら特に印象に残った内容や、実務で活かせそうだと感じたポイントをまとめていきます。

## 対象読者
- REST APIをこれから設計する人
- APIは普段使うが、設計を体系的に学んだことがない人
- PMやテックリードとしてAPI設計の基本を押さえたい人


## APIエンドポイント設計で意識したいこと

APIのエンドポイントは、利用者が最初に目にするインターフェースです。
そのため、実装都合ではなく「利用する開発者が理解しやすいか」という観点で設計することが重要だと感じました。

### URIを見ただけで役割が分かるようにする

エンドポイントは、そのURIを見ただけで何を扱うAPIなのか想像できる状態が理想です。

例えば `/products/12345` であれば「商品ID 12345の商品情報を扱う」と推測できます。
一方で、`/getdata?id=12345` のようなURIでは、何のデータを取得するAPIなのか判断できません。

APIを利用する開発者は仕様書だけでなくURIそのものも参考にするため、リソース名を明確に表現することが大切です。

### シンプルなURIを心がける

URIには必要以上の情報を含めない方が分かりやすくなります。

例えば、

* `/products/12345`
* `/users/100`

のような形式であれば、どのリソースを扱うAPIなのか一目で分かります。

一方で、

* `/service/api/getProductInformation/product/12345`

のように実装上の都合や冗長な表現が含まれると、可読性が低下してしまいます。

### 略語よりも分かりやすさを優先する

URIは開発者同士の共通言語でもあります。
そのため、文字数を減らすことよりも、誰が見ても意味を理解できることを優先した方がよいとされています。

例えば `products` を `prod` にしたり、`users` を `usr` にしたりすると、プロジェクト参加者によって解釈が分かれる可能性があります。

### 命名ルールを統一する

エンドポイントごとに命名規則が異なると、利用者は毎回ルールを覚え直さなければなりません。

例えばREST APIでは、

* 作成: `POST /products`
* 取得: `GET /products/{id}`
* 更新: `PUT /products/{id}`
* 削除: `DELETE /products/{id}`

のように、HTTPメソッドで操作を表現する設計が一般的です。
リソース名とHTTPメソッドの役割を統一することで、API全体の学習コストを下げられます。

### 将来の拡張を考慮した構造にする

APIは一度作って終わりではなく、後から機能追加されることがほとんどです。
そのため、新しい関連リソースを自然に追加できる構造にしておくと運用しやすくなります。

例えば商品レビュー機能を追加する場合、

`/products/{id}/reviews`

のような形で関連性を表現できれば、利用者も迷いにくくなります。

### 実装の都合をURIに持ち込まない

利用者が知りたいのは「どのリソースにアクセスできるか」であり、そのデータがデータベースに保存されているのか、別サービスから取得されているのかは本来関係ありません。

そのため、

`/database/products/12345`

のような実装依存のURIではなく、

`/products/12345`

のようにリソースを中心に表現する方が変更にも強い設計になります。

## HTTPメソッドとエンドポイントの役割分担

REST APIでは、URIとHTTPメソッドを組み合わせてリソースを操作します。
ここで重要なのは、「何を操作するのか」はURIで表現し、「どのような操作をするのか」はHTTPメソッドで表現するという考え方です。

例えば、ユーザー情報を扱うAPIであれば、`/users/123` というURIが対象リソースを表し、取得・更新・削除といった操作はHTTPメソッドによって区別します。

| 操作 | HTTPメソッド    | 例                 |
| -- | ----------- | ----------------- |
| 取得 | GET         | GET /users/123    |
| 作成 | POST        | POST /users       |
| 更新 | PUT / PATCH | PUT /users/123    |
| 削除 | DELETE      | DELETE /users/123 |

このように役割を分離することで、URIの設計がシンプルになり、API全体の一貫性も保ちやすくなります。

### GETはデータ取得のために利用する

GETはリソースを取得するためのメソッドです。

例えばユーザー情報の取得であれば、以下のような形になります。

```text
GET /users/123
```

GETは原則としてサーバー上の状態を変更しない操作に利用します。
そのため、GETリクエストを実行しただけでデータが更新されたり削除されたりする設計は避けるべきとされています。

### POSTは新しいリソースの作成に利用する

POSTは新しいリソースを登録する際に使用します。

```text
POST /users
```

### PUTとPATCHは更新処理で使い分ける

更新系の処理ではPUTとPATCHが利用されます。

PUTはリソース全体を更新するケースで利用されます。

```text
PUT /users/123
```

一方でPATCHは、一部の項目だけを変更したい場合に利用します。

```text
PATCH /users/123
```

実際の業務でもプロフィールの一部だけを更新するケースは多いため、PATCHが採用される場面は少なくありません。

### DELETEはリソース削除を表現する

リソースの削除にはDELETEを利用します。

```text
DELETE /users/123
```

### HTTPの仕組みを活用する

REST APIでは、操作をURIに埋め込むのではなくHTTPメソッドで表現します。
また、処理結果はHTTPステータスコードで表現し、認証情報やコンテンツタイプはHTTPヘッダーで表現できます。

独自ルールを増やすのではなく、既存の標準仕様を活用することで、API利用者の学習コストを下げられます。

例えば、

```text
POST /createUser
GET /getUser
DELETE /deleteUser
```

のような設計よりも、

```text
POST /users
GET /users/123
DELETE /users/123
```

の方がHTTPの仕組みを自然に活用でき、一貫性のあるAPIになります。

## SNSを例に考えるエンドポイント設計

本書ではSNSを例にエンドポイント設計が説明されていました。

### リソース名は複数形で表現する

リソースの集合を表す場合は複数形を利用します。

```text
/users
/posts
/friends
```

複数形に統一することで、API全体の命名ルールが分かりやすくなります。

### リソースIDで個別データを表現する

特定のユーザーを表す場合はIDをパスに含めます。

```text
/users/123
```

これにより、「ユーザー一覧」と「特定ユーザー」を自然に区別できます。

### 関係性はURIの階層で表現する

SNSではユーザーと友達のように関連するデータが存在します。

例えば、特定ユーザーの友達一覧を取得する場合は以下のようなURIが考えられます。

```text
/users/123/friends
```

この形式であれば、どのリソースに紐づくデータなのかが直感的に理解できます。

### 検索や絞り込みにはクエリパラメータを利用する

一覧取得時の検索条件はクエリパラメータで表現します。

```text
GET /users?name=john
GET /users?age=30
```

URIの構造を増やさずに検索条件を追加できるため、柔軟なAPI設計が可能になります。

## 検索機能とクエリパラメータ設計

一覧APIを設計する際には、「どのようにデータを検索するか」だけでなく、「大量のデータをどのように分割して取得するか」も考える必要があります。

特に利用者数やデータ量が増えるサービスでは、ページネーションの設計がAPIの使いやすさやパフォーマンスに大きく影響します。

### 一覧取得ではページネーションが重要

例えばユーザー一覧や投稿一覧を取得するAPIで、全件を一度に返してしまうとレスポンスサイズが大きくなり、通信量や処理時間が増加します。

そのため、多くのAPIではページネーションを利用して取得件数を制御します。

### オフセットページネーション

最も一般的なのが、取得件数やページ番号を指定するオフセットページネーションです。

例えば以下のような形式です。

```text
GET /users?page=3&per_page=50
```

この例では3ページ目の50件を取得します。

この方式は実装しやすく、利用者にも理解しやすいというメリットがあります。

一方で、データ件数が非常に多い場合は検索コストが高くなることがあります。
また、取得中にデータの追加や削除が発生すると、同じデータが重複して表示されたり、一部のデータを取りこぼしたりする可能性があります。

### カーソルページネーション

データ量が多いサービスや更新頻度の高いサービスでは、カーソルページネーションが利用されることがあります。

例えば、

```text
GET /posts?cursor=eyJpZCI6MTAwMH0=
```

のように、前回取得した位置を表す情報を利用して次のデータを取得します。

この方式では、特定の位置を基準にデータを取得するため、大量データでも効率的に検索しやすくなります。
また、取得中に新しいデータが追加された場合でも結果がずれにくく、SNSのタイムラインやチャットアプリなどで広く採用されています。

### 検索条件はクエリパラメータで表現する

検索や絞り込みを行う場合は、クエリパラメータを利用します。

例えば特定の名前で検索する場合は次のようになります。

```text
GET /users?first_name=ken
```

複数条件を組み合わせることもできます。

```text
GET /users?first_name=ken&last_name=suzuki
```

検索条件ごとにURIを増やす必要がないため、柔軟なAPI設計が可能になります。

### フリーワード検索という考え方

検索対象の項目を利用者に意識させたくない場合は、単一の検索パラメータを用意する方法もあります。

```text
GET /users?q=ken
```

この場合、名前やメールアドレスなど複数項目を横断して検索できるため、利用者にとって分かりやすいAPIになります。


## API利用者を識別する認証

APIでは、利用者が誰であるかを識別し、アクセス権限を制御する仕組みが必要になります。

本書ではOAuth 2.0についても説明されていますが、ここでは実際のAPI利用時によく目にするBearer Tokenを中心に整理します。

### Bearer Tokenとは

Bearer Tokenは、APIへアクセスするための認証情報です。

ログインや認証処理を行った後に発行され、クライアントは以降のAPIリクエストでこのトークンを送信します。
サーバーは受け取ったトークンを検証し、リクエスト元のユーザーや権限を判断します。

### Authorizationヘッダーで送信する

Bearer TokenはHTTPヘッダーの`Authorization`に設定するのが一般的です。

```http
GET /users/me HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...
```

サーバー側はトークンを検証し、認証済みユーザーとしてリクエストを処理します。

### URLやリクエストボディでの送信は避ける

トークンはクエリパラメータやリクエストボディで送信することも技術的には可能ですが、一般的には推奨されていません。

例えば以下のような形式です。

```text
GET /users?access_token=xxxxx
```

URLはログやアクセス解析ツールに記録される可能性があるため、認証情報の漏洩リスクがあります。

そのため、多くのAPIではAuthorizationヘッダーを利用する方式が採用されています。

### 有効期限を設ける

アクセストークンには有効期限を設定することが一般的です。
もしトークンが漏洩した場合でも、有効期限が短ければ被害を限定できます。

また、有効期限切れ後は再認証やトークン更新処理を行うことで、セキュリティと利便性のバランスを取ることができます。

## レスポンスデータ設計で意識したいこと

API設計というとエンドポイントやHTTPメソッドに注目しがちですが、実際にクライアントが利用するのはレスポンスデータです。

そのため、利用者が扱いやすいデータ構造になっているかどうかも重要な設計ポイントになります。

### JSONを前提に設計する

現在のWeb APIではJSONが事実上の標準になっています。
軽量で扱いやすく、多くのプログラミング言語で標準的にサポートされているためです。

そのため、新しくAPIを設計する場合は特別な理由がない限りJSONを選択すれば問題ないと感じました。

### DB設計とAPI設計は別物

データベースは効率的な保存を目的として設計されますが、APIは利用者の使いやすさを目的として設計されます。

例えば友達一覧APIを考えてみます。

以下のようにIDだけを返す設計も可能です。

```json
{
  "friendIds": [1, 2, 3]
}
```

しかし、この場合は各ユーザーの詳細情報を取得するために追加のAPI呼び出しが必要になります。

代わりに、

```json
{
  "friends": [
    {
      "id": 1,
      "name": "Taro"
    }
  ]
}
```

のように必要な情報をまとめて返した方が、クライアントは効率的に利用できます。

### Chatty APIを避ける

Chatty APIとは、必要な情報を取得するために何度もAPIを呼び出さなければならない設計のことです。

例えば友達一覧を取得するAPIが友達のIDしか返さない場合を考えます。

```json
{
  "friendIds": [1, 2, 3]
}
```

この場合、画面に友達の名前やプロフィール画像を表示するためには、

1. 友達一覧APIを呼び出す
2. ユーザーID 1 の詳細APIを呼び出す
3. ユーザーID 2 の詳細APIを呼び出す
4. ユーザーID 3 の詳細APIを呼び出す

というように複数回の通信が発生します。

一方で、友達一覧APIが必要な情報をまとめて返せば、1回のリクエストで画面表示に必要なデータを取得できます。

```json
{
  "friends": [
    {
      "id": 1,
      "name": "Taro",
      "profileImageUrl": "..."
    }
  ]
}
```

Chatty APIは通信回数の増加によるパフォーマンス低下や実装の複雑化につながるため、利用者のユースケースを考慮しながらレスポンスを設計することが重要です。


### データ項目名は分かりやすさを優先する

レスポンスのフィールド名は、API利用者が毎日目にするインターフェースです。

そのため、

* 一般的な単語を使う
* 略語を避ける
* 命名規則を統一する

といった基本的なルールが重要になります。

例えば、

```json
{
  "createdAt": "2026-07-20T10:00:00Z"
}
```

は直感的に理解できますが、

```json
{
  "crt_dt": "2026-07-20T10:00:00Z"
}
```

では意味を推測する必要があります。

APIは長期間利用されることが多いため、数文字の短縮よりも可読性を優先した方が良いと感じました。

### エラーもAPIの一部として設計する

正常系のレスポンスだけでなく、異常系の設計も重要です。

例えば認証エラーであれば、

```http
401 Unauthorized
```

存在しないリソースであれば、

```http
404 Not Found
```

のように適切なHTTPステータスコードを返します。

さらに、レスポンスボディにも機械的に処理しやすい形式でエラー情報を含めると利用者にとって親切です。

```json
{
  "error": {
    "code": "AUTHENTICATION_ERROR",
    "message": "Invalid access token"
  }
}
```

## 変更に強いAPIを設計する

APIは一度作ったら終わりではありません。
要件追加や仕様変更、新しい機能の追加など、運用を続ける中で変更が必要になる場面は必ず発生します。

特にAPIは複数のシステムをつなぐインターフェースの役割を持つため、安易な変更は利用側の不具合につながる可能性があります。
そのため、API設計では現在の要件だけでなく、将来的な変更への対応も考慮しておくことが重要です。

### 既存仕様の変更は慎重に行う

APIを利用するクライアントは、レスポンスの構造やデータ型を前提に実装されています。

例えば、

```json
{
  "userName": "Taro"
}
```

として提供していた項目を、

```json
{
  "name": "Taro"
}
```

へ変更すると、既存クライアントは期待したデータを取得できなくなります。
一見小さな変更に見えても、利用側にとっては破壊的変更になる場合があります。
そのため、公開済みのAPIを変更する際は影響範囲を十分に確認する必要があります。

### まずは後方互換性を意識する

例えば新しい情報が必要になった場合、

```json
{
  "id": 1,
  "name": "Taro",
  "email": "taro@example.com"
}
```

のようにフィールドを追加するだけであれば、多くのクライアントはそのまま動作します。

一方で、

* 項目名を変更する
* データ型を変更する
* 必須項目を増やす

といった変更は利用側への影響が大きくなります。
まずは既存利用者が継続利用できる方法がないかを検討することが重要です。

### APIのバージョニング

後方互換性を維持できない変更が必要な場合は、APIのバージョンを分ける方法があります。

例えば、

```text
/v1/users/123
/v2/users/123
```

のようにURIにバージョン番号を含める方法です。

利用者は移行タイミングを自分で判断できるため、既存システムへの影響を抑えながら新機能を提供できます。
実際に多くのサービスでも、この方式が採用されています。

### バージョンはむやみに増やさない

ただし、バージョンを増やせば解決するわけではありません。
サーバー側は複数バージョンを維持する必要がありますし、ドキュメントや運用コストも増加します。

そのため、

* 後方互換性を維持できる変更なら既存バージョン内で対応する
* 互換性を維持できない場合のみ新バージョンを作る

という考え方が現実的だと感じました。

### APIの廃止も設計の一部

新しいバージョンを提供し続けると、いずれ古いバージョンを廃止したくなる場面が出てきます。
その際に突然APIを停止してしまうと、利用者側で障害が発生する可能性があります。

そのため、

* 事前に廃止予定を通知する
* 移行期間を設ける
* 移行手順をドキュメント化する

といった対応が重要になります。

また、廃止済みAPIへのアクセスに対してはHTTPステータスコード `410 Gone` を返すことで、利用者に対して「このAPIは終了した」ことを明確に伝えられます。


## 堅牢なWeb APIを作るために

APIは機能を提供するだけでなく、安全かつ安定して利用できることも重要です。

特にAPIはプログラムから直接呼び出されるため、不正アクセスや大量リクエストの対象になりやすく、設計段階からセキュリティを考慮する必要があります。

### まずはHTTPSを前提にする

APIでは認証情報や個人情報を扱うことが少なくありません。
もしHTTP通信を利用していると、通信内容を第三者に盗み見られるリスクがあります。

そのため、APIはHTTPSを前提として設計し、通信経路を暗号化することが重要です。
現在ではほぼ必須の要件と言えます。

### 信頼してはいけないのはクライアント側

クライアントから送られてくる値を安易に信用してはいけません。

例えば以下のようなAPIがあるとします。

```json
{
  "userId": 123,
  "point": 1000
}
```

画面上ではポイントを1000に制限していたとしても、悪意のある利用者はリクエストを書き換えて送信できます。

そのため、

* ログインユーザー本人か
* 操作対象への権限があるか
* 値が妥当な範囲か

といった検証は必ずサーバー側で行う必要があります。

### 認可チェックを忘れない

認証と認可は似ていますが役割が異なります。

* 認証：誰なのかを確認する
* 認可：何ができるかを確認する

例えばログイン済みユーザーであっても、

```text
GET /users/999
```

へアクセスした際に、他人の個人情報が取得できてしまってはいけません。

APIでは認証だけでなく認可の設計も重要です。

### リプレイ攻撃や二重実行を考慮する

決済処理やポイント付与処理などでは、同じリクエストが複数回送信されるケースを考慮する必要があります。

例えば、

```text
POST /payments
```

を誤って複数回処理すると、二重決済が発生する可能性があります。

そのため、

* リクエストIDを持たせる
* トランザクションを管理する
* 重複実行を検知する

といった対策が必要になります。

### レートリミットで大量アクセスを防ぐ

APIは大量アクセスによってサービス全体へ影響を与える可能性があります。

そのため、多くのサービスではレートリミットを設けています。

例えば、

* 1分間に60回まで
* 1時間に5,000回まで

といった形で利用回数を制限します。

これにより、不正アクセスや意図しない大量リクエストからシステムを保護できます。

## さいごに

API設計というとエンドポイントやリクエスト・レスポンスの形式を決めることだと以前は考えていました。

しかし実際には、URI設計やHTTPメソッドの使い分けだけでなく、認証・認可、ページネーション、エラーハンドリング、バージョニング、セキュリティ対策まで含めて考える必要があることを学びました。

また、APIは一度作って終わりではなく、長期間運用され続けるインターフェースです。
そのため、現在の要件だけでなく、将来の変更や利用者の増加まで見据えて設計することの重要性も改めて認識しました。

今後は実装だけでなく、利用者にとって分かりやすく変更に強いAPI設計を意識しながら開発に取り組んでいきたいと思います。
